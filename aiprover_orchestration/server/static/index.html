Orchestrated formal proving in Lean

A theorem is submitted in mathematical language, optionally with an informal proof. The orchestration formalizes the statement in Lean, decomposes the proof into lemmas, and proves each lemma with AIProver; Lean then verifies the complete proof.

RunsThe progress and results of each proof attempt. ProjectsRelated results proved in dependency order on a shared library. SubmitSubmission of a single problem or a project. GuideThe operation of a run and the interpretation of its results.

Lean verifies each proof against its formal statement, but it cannot establish that the formal statement expresses the intended theorem. The orchestration assesses this correspondence; consequently, the formal statement should be read before a result is relied upon.

      Start a project

        A library is a Lean file that compiles on its own, without sorry. The run uses its definitions and may cite its theorems instead of proving them again. A zip of Lean files, with its root modules at the top level, becomes a package library: it is built on the chosen Lean version once, every file of the run imports it, and agents read its statements through their tools rather than in their prompts.
        Roles that use AIProver must use the same version. Each group has its own model server; runs of a group share it. Group cpu has none: use it when every role runs on Claude, Codex, or your own server.
        Orchestrator settings
        An empty field keeps the value shown, which runs use by default. A resumed run keeps its settings.

        A project proves connected results in dependency order on one shared library.

        Source files are unverified reference material, available to planning, research, and the orchestrator but not to the provers. LaTeX and other text files work best, PDF files are harder to search, and office documents should be converted first. They do not create results or add to the library, and a large upload slows every run.
